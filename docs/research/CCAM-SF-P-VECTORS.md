# CCAM-SF-P canonical vector corpus

**Status:** independently specified oracle corpus; no cross-executor harness or implementation-refinement theorem is claimed yet.  
**Format:** `capstan-ccam-sf-vectors/1`  
**Machine contract:** `docs/architecture/CCAM.md` (normative CCAM v0.1)  
**Proof profile:** `docs/research/CCAM-SINGLE-FRAME-PROOF-PROFILE.md`  
**Machine-readable corpus:** `verification/ccam_sf_vectors.json`

## Oracle conventions

- Each vector has an explicit ID, register types, return contract, initial profile entry, instruction budget, and instruction sequence using the normative v0.1 instruction field names.
- `expected.trace_pcs` lists the program counter fetched for each instruction actually executed. It does not include the PC at which a pre-dispatch instruction-limit trap occurs.
- `expected.steps` is the number of instructions actually dispatched. A halt or dynamic trap consumes one step; a pre-dispatch budget trap consumes none.
- Validation rejection means no machine is created and no instruction executes.
- Expected results are authored as test oracles; they are not generated by the Capstan evaluator or Lean model.
- `normative_validation` and `profile_validation` are separate on purpose. SF-019 is the required counterexample: normative CCAM permits unreachable final fall-through when no reachable path falls off the function, while CCAM-SF-P deliberately rejects it.
- `profile_entry` models the Lean `RawSingleFrameProgram.entry` field. It is not a field in the normative CCAM v0.1 JSON program; SF-020 checks the additional implementation-alignment predicate requiring entry zero.

## Important semantic boundary: explicit traps

The current Lean `MachineInstr.explicitTrap` constructor takes the finite `Trap` enumeration. The concrete CCAM `trap` opcode instead returns the machine code `explicit_trap` together with its validated application reason as detail. Those are not equivalent outcomes. SF-X01 is therefore retained as an explicit out-of-profile vector. Do not map an arbitrary reason to a similarly named finite machine trap, and do not count SF-X01 as Lean/Capstan agreement.

The first dual-execution corpus covers the finite built-in traps represented by the model: integer overflow, division by zero, uninitialised register and instruction-limit exhaustion. Other defensive traps (invalid register, type mismatch, invalid PC/opcode) arise from violating the validated evaluator precondition and are not positive in-profile vectors. Malformed operands belong to validation tests, not execution traces.

## Execution and proof status

This file is the canonical oracle data for the next harness increment. It is not yet consumed by either implementation. The next work must:

1. Add strict schema validation for the corpus itself (duplicate IDs, exact fields, signed-64 literal bounds, valid indices and trace consistency).
2. Add a Capstan-native corpus runner that constructs `CCAMInstruction` values and checks validation, outcome, trace and step count.
3. Add a Lean corpus reader/adapter or a generated Lean fixture from this same source file. Generation must be deterministic and must not generate expected outcomes from either executor.
4. Define the complete machine-state relation, reusing `RuntimeBridge.lean` and `NativeRegisterBridge.lean`; do not recreate the register relation.
5. Prove the initial-state correspondence and instruction-level simulation, then exact budget correspondence.
6. Run both suites and the Lean build/checker on the same exact commit in CI.

Until these steps pass, this corpus is an independently specified oracle, not evidence of cross-model conformance or formal implementation refinement.
