# K0: Linux kernel CVEs of 2025 against Capstan

Generated by `tools/k0/study.py` from the CVE List; do not edit by hand. The method, its limits and every rule are below, so the result can be checked and re-run each year ([DESIGN-MAP.md](DESIGN-MAP.md), section 7, K0).

## Result

**2,702 CVEs** published in 2025 by the Linux kernel's CVE Numbering Authority.

| Outcome had the code been written in Capstan | CVEs | Share of all | Share of those classified |
|---|---|---|---|
| Prevented at compile time | 1,081 | 40.0% | 50.9% |
| Stopped safely at run time | 423 | 15.7% | 19.9% |
| Logic error: beyond any language | 175 | 6.5% | 8.2% |
| Outside Capstan's current reach | 446 | 16.5% | 21.0% |
| Not determinable from the record | 577 | 21.4% |  |

- **70.8% of the classified CVEs** (1,504) are weaknesses Capstan prevents today: 50.9% refused by the compiler, 19.9% stopped safely at run time.
- **48.1% of all CVEs** (1,299) are memory-safety bugs: use-after-free, double free, out-of-bounds access, NULL dereference and uninitialised memory.
- **21.0%** are outside Capstan's current reach, mostly concurrency and resource lifetime: the kernel-mode prerequisites in K1 are aimed at exactly these.
- **8.2%** are logic errors that no programming language prevents.

A safe stop in the kernel is still a crash (a denial of service), but not a corruption an attacker can turn into code execution or privilege escalation.

## Kernel adjustments to the atlas

The atlas judges Capstan as it is today, for application code. Where its verdict depends on a feature kernel code cannot use, or on a construct Capstan simply lacks, the study counts the class as outside Capstan's reach rather than prevented:

| CWE | Why the atlas verdict does not carry over to the kernel |
|---|---|
| CWE-401 | Leaks are collected by Capstan's garbage collector, but kernel code cannot use a collector that pauses at arbitrary moments. Needs deterministic memory management (K1). |
| CWE-772 | Capstan has no handles to leak today; kernel code holds reference counts, locks and device resources. Needs ownership of resources (K1). |
| CWE-362 | Capstan has no threads yet, so races are inexpressible only because concurrency is. Needs safe concurrency (v0.7, K1). |
| CWE-667 | As CWE-362: locking is absent from the language, not checked. Needs safe concurrency (v0.7, K1). |
| CWE-833 | As CWE-362. Needs lock ordering checked by the compiler (v0.7, K1). |
| CWE-843 | Capstan has no casts, but kernel code must reinterpret device memory and container structures. Needs typed hardware access under proof (K1). |
| CWE-1335 | Capstan has no shift operators yet; kernel code needs them. A checked shift, like checked arithmetic, is the natural rule (to be designed). |
| CWE-1037 | Speculative-execution leaks are a property of the processor, not of the source language. |
| CWE-617 | A kernel WARN_ON or BUG_ON was reached, but the record does not say what state reached it, so the underlying weakness is unknown. |

Use-after-free and double free are counted as prevented: Capstan has no `free()`, and the deterministic memory management planned for kernel code (K1) must keep that guarantee, as Rust's ownership does. Some of these use-after-frees begin as races (a work item running after its device is gone); the memory error is prevented, the race itself may remain a logic error.

## Method

1. **Data.** Every record in the [CVE List](https://github.com/CVEProject/cvelistV5) whose assigner is the Linux kernel CNA and whose publication date falls in 2025. Rejected records are excluded. Snapshot: commit `e86f5b7a53ee`.
2. **Classification.** The kernel CNA almost never assigns a CWE, so each CVE is classified from its description, which is the fix commit's message: its subject line, its text, and the sanitiser reports quoted in it (KASAN, UBSAN, KMSAN, KCSAN, lockdep, kmemleak). The rules are regular expressions in `tools/k0/classify.py`, tried in a fixed order. Memory-safety classes are tried first, so a race that ends in a use-after-free counts as a use-after-free: that is what a language has to stop.
3. **The atlas.** Each class's CWE is looked up in the [CWE atlas](CWE-ATLAS.md), taking its weakest verdict, then the kernel adjustments above are applied.
4. **Check.** 40 CVEs drawn at random were labelled by reading each fix, before looking at the classifier's answer (`tests/k0/labels-heldout.csv`). The classifier gives the same class for 24 (60.0%) and the same outcome for 28 (70.0%). It counts 21 of the 40 as prevented; the hand labels count 21, so its errors do not inflate the headline.
   On the 60-CVE sample used while writing the rules (`tests/k0/labels.csv`) the figures are 85.0% and 85.0%. Both samples were labelled by the AI assistant that wrote the classifier; independent relabelling is the next step.

## Limits

- Classification is automatic. A description can mention a class it does not fix, and many state the symptom rather than the cause. The per-CVE table (`tools/k0/data/`) lets anyone check a row.
- A CVE is not an exploit: the kernel CNA assigns one to almost every fix that might matter. The study measures weakness classes, not attacks.
- "Prevented" means the weakness could not be written, not that the driver would have been bug-free: the same mistake in Capstan becomes a compile error or a safe stop, and the programmer must still fix it.
- Kernel-mode Capstan (K1) does not exist yet. These are the classes its rules must cover, measured against the language as it stands.
