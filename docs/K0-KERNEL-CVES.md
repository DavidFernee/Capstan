# K0: Linux kernel CVEs of 2025 against Capstan

> **Superseded — do not use the figures below as a complete 2025 population or current kernel-safety claim.** The previous loader searched only CVE identifier years 2024 and 2025, omitting delayed publications assigned in earlier years. The classifier also allowed non-memory matches in a title to outrank memory-safety consequences in the CNA body. It also treated use-after-free and double-free prevention as a present kernel capability even though kernel ownership/lifetime enforcement is a K1.1 requirement, and described K1.10 proof-eligible classes as if they were proved absent without concrete proof evidence. The loader and projection rules have been corrected; regenerate this report and its CSV/JSON outputs from a complete, pinned CVE List V5 checkout before quoting any percentages. The historical figures below are retained only to preserve the audit trail.

Generated by `tools/k0/study.py` from the CVE List; do not edit by hand. The method, its limits and every rule are below, so the result can be checked and re-run each year ([DESIGN-MAP.md](DESIGN-MAP.md), section 7, K0).

## Result

**2,702 CVEs** published in 2025 by the Linux kernel's CVE Numbering Authority. 2,114 were classified automatically from their fix descriptions and 588 were read and classified by a reviewer, because the rules could not decide them or decided them wrongly. 4 remain undeterminable from the record.

| Outcome had the code been written in Capstan | Today | With K1.1 to K1.9 | With K1.10 proofs |
|---|---|---|---|
| Prevented at compile time | 43.6% | 60.8% | 60.8% |
| Stopped safely at run time | 17.0% | 18.3% | 18.3% |
| Proved absent against a specification | – | – | 19.6% |
| Logic error: beyond any language | 18.7% | 20.8% | 1.2% |
| Outside Capstan's current reach | 20.7% | 0.1% | 0.1% |
| **Prevented or proved absent** | **60.6%** | **79.1%** | **98.7%** |

Shares are of the 2,698 CVEs whose weakness is known. Today's column is a measurement of Capstan as it stands; the other two are projections of designs in [DESIGN-MAP.md](DESIGN-MAP.md) section 7, which hold only if those designs are built as specified, and which K2 tests on real kernel code.

- **52.4% of all CVEs** (1,415) are memory-safety bugs: use-after-free, double free, out-of-bounds access, NULL dereference and uninitialised memory. This is a weakness count, not a claim that kernel-mode Capstan currently prevents them; use-after-free and double-free coverage depends on K1.1 ownership.
- **60.6% are prevented today**: 43.6% refused by the compiler, 17.0% stopped safely at run time.
- A safe stop in the kernel is still a crash (a denial of service), but not a corruption an attacker can turn into code execution or privilege escalation.

### What no design here removes

34 CVEs (1.3%) stay possible even with every design item, and 4 cannot be judged:

| Class | CVEs | Why |
|---|---|---|
| hardware or firmware fault | 30 | The device, firmware or processor misbehaves; the driver's workaround is a correct program for a wrong machine. |
| build or configuration error | 2 | The mistake is in the build or device-tree configuration, not in code. |
| speculative execution | 2 | Processor flaws beyond Spectre variant 1 (branch-history injection, VMSCAPE): Capstan applies the vendor's barriers, but the leak is in the hardware. |

K1.10's proofs apply to the logic errors only where the component's behaviour is specified, and a proof is only as good as its specification. The study counts every logic error in a provable class as proved absent, so that column is the ceiling the design aims at, not a forecast.

## Kernel adjustments to the atlas

The atlas judges Capstan as it is today, for application code. Where its verdict depends on a feature kernel code cannot use, or on a construct Capstan simply lacks, the study counts the class as outside Capstan's reach rather than prevented:

| CWE | Why the atlas verdict does not carry over to the kernel |
|---|---|
| CWE-401 | Leaks are collected by Capstan's garbage collector, but kernel code cannot use a collector that pauses at arbitrary moments. Needs deterministic memory management (K1). |
| CWE-772 | Capstan has no handles to leak today; kernel code holds reference counts, locks and device resources. Needs ownership of resources (K1). |
| CWE-362 | Capstan has no threads yet, so races are inexpressible only because concurrency is. Needs safe concurrency (v0.7, K1). |
| CWE-667 | As CWE-362: locking is absent from the language, not checked. Needs safe concurrency (v0.7, K1). |
| CWE-833 | As CWE-362. Needs lock ordering checked by the compiler (v0.7, K1). |
| CWE-843 | Capstan has no casts, but kernel code must reinterpret device memory and container structures. Needs typed hardware access under proof (K1). |
| CWE-1037 | Speculative-execution leaks are a property of the processor, not of the source language. |
| CWE-617 | A kernel WARN_ON or BUG_ON was reached, but the record does not say what state reached it, so the underlying weakness is unknown. |

Classes found only in review are judged the same way: use after device removal (CWE-672), misaligned access and aliased mutation of a shared buffer have no counterpart in Capstan today, so they count as outside its reach until K1.5, K1.6 and K1.1. Hardware faults and build errors are beyond any language.

Use-after-free and double free are not counted as prevented today in kernel code. The application memory model does not establish lifetimes for kernel allocators, DMA, callbacks or externally owned objects. Their K1 projection is conditional on K1.1 ownership and lifetime enforcement.

## Method

1. **Data.** Every record in the [CVE List](https://github.com/CVEProject/cvelistV5) whose assigner is the Linux kernel CNA and whose publication date falls in 2025. Rejected records are excluded. Snapshot: commit `e86f5b7a53ee`.
2. **Automatic classification.** The kernel CNA almost never assigns a CWE, so each CVE is classified from its description, which is the fix commit's message: its subject line, its text, and the sanitiser reports quoted in it (KASAN, UBSAN, KMSAN, KCSAN, lockdep, kmemleak). The rules are regular expressions in `tools/k0/classify.py`, tried in a fixed order. Memory-safety classes are tried first, so a race that ends in a use-after-free counts as a use-after-free: that is what a language has to stop.
3. **Review.** Every CVE the rules could not decide, and every one they called speculative execution, was read and classified by a reviewer (588 in all, `tools/k0/data/reviewed-2025.csv`). The review label replaces the automatic one. Where a fix states its consequence ("leads to a NULL dereference"), the consequence decides, as in step 2.
4. **The atlas.** Each class's CWE is looked up in the [CWE atlas](CWE-ATLAS.md), taking its weakest verdict, then the kernel adjustments above are applied.
5. **Check.** 40 CVEs drawn at random were labelled by reading each fix, before looking at the classifier's answer (`tests/k0/labels-heldout.csv`). The automatic classifier gives the same class for 24 (60.0%) and the same outcome for 28 (70.0%). It counts 21 of the 40 as prevented; the hand labels count 21, so its errors do not inflate the headline.
   On the 60-CVE sample used while writing the rules (`tests/k0/labels.csv`) the figures are 85.0% and 85.0%.

## Limits

- The review and both check samples were done by Claude, the AI assistant that wrote the classifier. An independent reviewer relabelling them is the next step for the study's credibility.
- The automatic classification is right about 60% of the time on class and 70% on outcome (held-out sample); it does not overstate prevention there, but individual rows can be wrong. Every row is in `tools/k0/data/` with how it was classified.
- Review read the fix descriptions, not the code changes. Reading the diffs would settle the four undeterminable CVEs and some borderline logic errors.
- A CVE is not an exploit: the kernel CNA assigns one to almost every fix that might matter. The study measures weakness classes, not attacks.
- "Prevented" means the weakness could not be written, not that the driver would have been bug-free: the same mistake in Capstan becomes a compile error or a safe stop, and the programmer must still fix it.
- Kernel-mode Capstan (K1) does not exist yet. The projections say which classes its rules must cover.
