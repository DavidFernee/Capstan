# v0.5 type-system design proposal

**Status:** design proposal; not yet part of the language specification  
**Target:** Capstan v0.5 — Abstraction

This document turns the v0.5 roadmap items into an implementable design. It is deliberately conservative: static checking, bounded compiler work, no implicit dynamic dispatch, no exceptions, and no lifetime mechanism that depends on programmer discipline.

## 1. Goals and non-goals

v0.5 adds user-defined generic structs, enums and functions; interface constraints with static dispatch; explicit module visibility; closures with by-value capture; Result<T, E> and ? error propagation.

It does not add inheritance, subtyping, runtime reflection, exceptions, unchecked casts, reference-capturing closures, or general-purpose dynamic dispatch. Concurrency and asynchronous execution remain v0.7.

The compiler must reject a program before code generation if its types, interface obligations, visibility or control-flow rules cannot be established.

## 2. Generic declarations

Proposed syntax:

    struct Box<T> { T value; }
    enum Option<T> { Some(T value), None }
    T identity<T>(T value) { return value; }
    Box<int> b = new Box<int>{value: identity(7)};

Type parameters are introduced after the declaration name. Generic arguments use the existing angle-bracket type syntax. Nested types are allowed, and the lexer/parser must preserve the existing treatment of adjacent > tokens in nested generic types and shifts.

Generic arguments are inferred from value arguments at calls where there is exactly one valid solution. Type parameters that cannot be inferred from function arguments are a compile-time error; explicit type arguments are available where inference would otherwise be ambiguous. No inference may depend on runtime values.

Generic parameters are invariant. There is no implicit subtype conversion, covariance or contravariance. A generic type is assignable only when its arguments are exactly equal after substitution.

## 3. Interfaces and constraints

Proposed syntax:

    interface Comparable<T> {
        bool less(T self, T other);
    }

    impl Comparable<int> for int {
        bool less(int self, int other) { return self < other; }
    }

    T maximum<T: Comparable<T>>(T a, T b) {
        if (a.less(b)) { return b; }
        return a;
    }

An interface declares required method signatures. An impl supplies those methods. The checker verifies the implementation's method set, parameter and return types, visibility and safety rules before accepting it.

Interface dispatch is static. The compiler resolves the implementation at each generic instantiation and emits a direct call; there is no vtable or runtime type test. A type/interface pair has at most one implementation in a compilation unit. Overlapping implementations are rejected, never resolved by source order.

A generic body may use only operations supplied by its declared constraints. The checker must not infer an interface implementation merely because a type happens to have a method with the same name.

## 4. Monomorphisation and resource bounds

The initial implementation will use monomorphisation: each concrete instantiation gets a concrete checked representation and generated C type/function. This avoids runtime type erasure and keeps interface calls direct.

The compiler must substitute type parameters structurally and recursively; type-check each concrete instantiation after substitution; memoise identical instantiations; detect recursive instantiation cycles; impose a per-template instantiation limit and maximum depth; fail with a normal diagnostic before exhausting memory or the compiler stack; and include instantiated type arguments in diagnostics and generated symbol names.

Proposed initial limits are 256 distinct instantiations per generic declaration and depth 32. These are conservative starting points, subject to stress testing. Tests must cover adversarially expanding types and mutually recursive generic calls.

No generic template may be emitted as partially checked C. Code generation consumes only fully checked concrete instantiations.

## 5. Result and error propagation

Result<T, E> is a generic sum type, expressible with the generic enum mechanism:

    enum Result<T, E> {
        Ok(T value),
        Err(E error)
    }

A function returning Result<T, E> may use postfix ? on another Result<U, E> expression. On Ok(value), the expression yields value; on Err(error), it returns Err(error) from the current function.

The error type must match exactly. v0.5 will not perform implicit error conversions or invoke user conversion code during propagation. ? is rejected in a function that does not return a compatible Result. It is also rejected for optionals; optional unwrapping remains explicit through if (let ...).

There are no exceptions, implicit unwinds or hidden control transfers. Every propagation edge is visible in the typed control-flow representation and covered by tests for both variants.

## 6. Module visibility

Each source file is a module, matching the compiler's existing file identity. Top-level declarations are private by default. public explicitly exports a declaration; private may be written to make the intent visible.

A module may access its own private declarations. Other files may refer only to public declarations. This applies to types, functions, constants, enums and interfaces, and is checked at every reference site, not merely when resolving imports. A public declaration may not expose a private type in its public signature or fields.

The entry point may remain private. Existing multi-file programs will need explicit public annotations on declarations intentionally used by other files; migration diagnostics must identify the exporting file and inaccessible declaration. The compiler must not silently widen visibility to preserve old behaviour.

The compiler also supports an `opaque struct` declaration modifier: all fields of that
struct are private to its defining source-file module, with no per-field annotation required.
This is the preferred representation boundary for resource-owning and invariant-bearing types.
It does not imply affine ownership or lifetime checking; those remain separate type-system gates.

Struct-field visibility is a separate mechanism from top-level module exports. The initial field-encapsulation slice supports an explicit `private` modifier on a field; unmodified fields remain public for source compatibility. Private field reads, writes and struct-literal initialisation are accepted only in the source file that defines the struct. This preserves the defining module as the invariant-owning boundary even though imported files are currently flattened into one compilation unit. A module can expose factory functions and methods while keeping representation fields inaccessible to importers. Private methods, friend declarations, default-private fields and ownership/lifetime guarantees are deliberately not implied. Every cross-file access path must be rejected by the checker, including reads, writes, nested expressions and aggregate construction.

## 7. Closures

Proposed expression syntax:

    int offset = 4;
    fn(int) -> int add_offset = |int x| x + offset;

A closure stores a code pointer and an environment containing copies of all free-variable bindings at closure creation. There is no reference capture syntax. The compiler computes the free-variable set and capture layout; callers cannot omit a capture or request a mutable reference capture.

Capture is by value of the binding. For scalar values and immutable strings this is a value snapshot. For reference types, the pointer is copied and the referenced object remains shared and mutable; this is not a deep clone. The tracing garbage collector keeps captured objects alive, so a closure cannot retain a dangling stack reference.

A closure may not capture Grant<P>: grants are request-scoped and must not escape into a heap environment. Returning or storing a grant remains prohibited. Capturing Secret is permitted only if the generated environment is allocated and reclaimed using the secret-aware runtime path, so the secret bytes are wiped when the environment is collected.

Function types are structural and invariant. A closure is callable only through its checked function type. No conversion from arbitrary function pointers or foreign code pointers is implicit.

## 8. Security invariants

The implementation is incomplete until tests establish all of the following:

1. Type substitution cannot turn Tainted into trusted string, Secret into printable text, or bypass any existing sink rule.
2. Generic constraints are checked at every instantiation; an unimplemented or ambiguous interface never reaches code generation.
3. No duplicate or overlapping interface implementation can make dispatch depend on declaration order.
4. Instantiation depth and count limits stop compiler resource-exhaustion attacks with diagnostics.
5. A private declaration cannot be reached through an imported file, alias, nested type, method, interface implementation or generic signature.
6. A public signature cannot leak a private type.
7. ? propagates only a typed Err of the exact enclosing error type; it cannot swallow or reinterpret an error.
8. Closures capture all and only the required bindings by value; grants cannot escape through captures, returns, containers or nested closures.
9. Captured references remain GC-reachable after the creating stack frame returns.
10. Generated C remains warning-free under GCC and Clang, and behaviour agrees across -O0, -O2 and -O3.

Every new checker rejection needs a negative test; every runtime-sensitive behaviour needs a positive and stress test. The compiler's self-hosting bootstrap and mutation/fuzz suites must exercise the new syntax and type paths.

## 9. Implementation order

1. Generalise the type representation and parser for named type parameters and generic arguments; add parser-only and rejection tests.
2. Implement generic struct/enum substitution and monomorphised layout.
3. Implement generic functions, argument-based inference, instantiation caching and hard resource limits.
4. Add interfaces, coherence checks and static dispatch.
5. Add Result<T, E> and ? as typed control flow.
6. Add module visibility and migrate repository modules explicitly.
7. Add function types and by-value closures, including GC and grant-capture rules.
8. Update SPEC.md, the compiler bootstrap, examples, Shroud's typed View<M> API and the design map only as each feature passes its tests.

The order is intentional: closures and Shroud's typed messages depend on generic function/type machinery; error propagation depends on generic enums; and module visibility is best enforced once generic signatures and interface declarations are represented uniformly.


## 10. Runtime representation and garbage-collector contract

The first implementation must preserve the runtime's existing conservative tracing
contract. The collector scans physical pointer-bearing allocations; it does not
consult generic type arguments or per-field pointer maps. Therefore:

- User-defined struct and enum specialisations, including generic specialisations,
  use traced allocation kind 0 by default. A specialisation may use pointer-free
  kind 1 only after the compiler proves the complete substituted layout contains
  no pointers and every construction, copy, mutation, collection, sort and root
  path preserves that fact.
- Generic list/map backing storage retains the existing traced representation.
  A scalar-looking instantiation does not justify changing its allocation kind:
  erased collection slots may contain boxed optionals or references, and the
  collector must continue to see those pointers.
- A Secret value is a reference to a separate pointer-free kind-2 payload.
  A struct, enum, list, map or closure environment containing a Secret reference
  remains pointer-bearing kind 0. Never place a Secret payload inline in a
  traced aggregate or classify the aggregate itself as kind 2.
- A closure environment containing references uses kind 0 and is traced. Capturing
  a Secret copies its reference into that environment; the environment keeps the
  separate kind-2 payload reachable until the closure becomes unreachable.
  The collector's eventual wipe is best-effort reclamation, not deterministic
  destruction at closure scope exit. The design must not promise a wipe deadline.
- Global roots are registered according to the fully substituted generated C
  representation. Register every non-scalar pointer slot before any initializer
  that can allocate; do not infer pointer-freedom from an unresolved type variable.
- Generic lowering and closure construction must preserve the compiler/runtime
  allocation-safepoint contract: keep owners and incoming pointer values live
  across allocating operations, and do not place pointer-bearing data in atomic
  storage.

These rules are correctness-first constraints for the initial monomorphising
backend. Any later specialised representation requires a separate layout proof,
generated-C audit, root/GC-stress tests and differential validation.
