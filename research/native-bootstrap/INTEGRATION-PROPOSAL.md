# Native compiler bootstrap — integration proposal (provisional)

**Status:** B3 planning draft; no shared implementation changes authorised or made.
**Baseline:** `main` at `189f19dd2a39c169e033691856d675b070fb2864`.
**Work branch:** `research/native-compiler-bootstrap`.
**Coordination:** issue #370.

This proposal identifies likely files, interfaces and review boundaries for integrating the native compiler programme after the existing integration worker stabilises the relevant mainline interfaces. It is deliberately not a request to rebase, merge, retarget or alter another worker's branch or PR. Every implementation PR below must be cut from a refreshed mainline after issue #370 coordination and must not depend on unmerged code except where explicitly gated.

## 1. Current state and constraints

- The baseline mainline contains a scalar CCAM evaluator, multi-function call model, checked scalar lowering and a Linux x86-64 freestanding assembly emitter.
- Baseline CI run [45695354353](https://github.com/DavidFernee/Capstan/actions/runs/45695354353), Ubuntu/GCC job 139491217684, passes ten direct native executable tests.
- The current native test route is generated by `verification/ccam_native_x64.cap` and run by `tests/run.sh`; the harness remains in the legacy compiler/test environment.
- The native emitter's integer entry result currently goes through Linux exit status (8-bit observation), and trap/failure detail is collapsed. These contracts must be resolved before asserting full CCAM outcome equivalence.
- The strict ELF inspection helper is isolated at `research/native-bootstrap/check-elf.sh`; it is not yet wired into shared tests.
- The actual compiler requires strings, generic lists/maps, AST/type graphs, optional values, source/import IO and a larger runtime than the scalar native subset.

## 2. Proposed PR sequence and boundaries

### N0 — Native result and terminal-observation contract

**Purpose:** make native execution outcomes precise before expanding the language subset.

Likely files:
- `docs/architecture/CCAM.md` — specify the observable result/trap contract and any native execution profile.
- `verification/ccam_native_x64.cap` — implement the approved result/trap representation and distinguish failure classes.
- `verification/ccam_calls.cap` and `verification/ccam_core.cap` — only if the agreed canonical semantics or test-visible state needs a change; avoid incidental edits.
- `tests/run.sh` — add full-width result and structured-trap cases to the native execution harness.
- `research/native-bootstrap/check-elf.sh` — keep stronger binary inspection separate until reviewed for test integration.

Required interface:
- A versioned, bounded terminal result record distinguishing normal return, explicit trap, arithmetic trap, step/depth exhaustion, invalid state and platform/resource failure.
- Signed-64 result encoding that does not depend on process exit status.
- Exact trap reason/code and source location fields where specified by CCAM.
- A bounded output transport contract (designated fd or equivalent), including short-write, interruption, output cap and failure behavior. The executable must not silently truncate an int64 value.
- Exit status reserved for process-level success/failure of the transport, not used as the sole CCAM value channel.

Dependencies: canonical CCAM semantics and stable multi-function interfaces. Do not consume PR #304 byte-output extension or PR #315 JSON decoder for this PR.

Acceptance:
- Full signed-64 boundary values survive the result protocol.
- Every terminal outcome has an unambiguous record.
- Existing scalar test corpus agrees on values, traps, step count and depth.
- Output transport is bounded and deterministic under short write/failure.
- No C runtime, libc or dynamic loader dependency in the emitted program.
- ELF checks include no PT_INTERP, no dynamic section, no undefined symbols, no relocations, W^X LOAD segments and non-executable GNU_STACK.

### N1 — Strict CCAM interchange and admission boundary

Likely files:
- The exact decoder/validator paths from PR #315 after it is merged and stabilised.
- `docs/architecture/CCAM.md` for the canonical external format.
- New conformance vectors under `verification/` only if PR #315's existing vectors do not cover required adversarial cases.

Required interface:
- Versioned format with exact integer representation.
- Duplicate object keys rejected before semantic decoding.
- Closed object/enum schemas and rejection of unknown fields/opcodes.
- Explicit limits for bytes, nesting, token count, functions, instructions, registers, strings, arguments and total work.
- Deterministic decoder errors separated from well-formed CCAM execution traps.
- Whole-program validation completes before execution or code generation.

Dependency: PR #315 Linux CI failures resolved, public API stable, merged to main. No parallel decoder in this workstream.

Acceptance: decoder vectors, malformed/mutated corpus, exact integer edge cases, resource exhaustion and agreement with the canonical schema. Any formal claim requires a theorem connecting the implementation to the decoder model.

### N2 — Concrete native memory and object model

Likely new files (names provisional):
- `runtime/native/memory.cap` — bounded allocator/arena and allocation accounting.
- `runtime/native/object.cap` — object headers, typed references and object layouts.
- `verification/native_memory_model.cap` or a Lean model — state and invariant model.
- `docs/architecture/NATIVE-MEMORY-MODEL.md` — normative ownership/lifetime contract.

Likely existing interfaces requiring later integration:
- `compiler/ast.cap` — AST/type object representation.
- `verification/ccam_core.cap` and `verification/ccam_calls.cap` — only if heap/reference semantics become part of the CCAM machine, under a separately reviewed semantic version.

Required interface:
- Checked size/alignment arithmetic; hard heap budget; deterministic OOM.
- Explicit ownership/lifetime and aliasing model.
- Stable AST references across collection growth.
- Failure-atomic allocation and collection mutation.
- No safe raw-pointer operations or ambient authority.
- Defined object initialization and invalid-reference behavior.
- No assumption that the abstract region/heap models are a concrete implementation.

Dependencies: design decision and coordination around PRs #246, #262 and #255; do not duplicate or pre-empt their work. PRs #371/#372 are not accepted as completed concrete implementation refinement.

Acceptance: allocator/object invariants, adversarial allocation/overflow tests, OOM failure-atomicity, alias/lifetime tests, fuzzing, and an implementation-linked refinement argument before any formal claim.

### N3 — Native strings and collections

Likely new files:
- `runtime/native/strings.cap`
- `runtime/native/list.cap`
- `runtime/native/map.cap`
- matching `verification/` conformance vectors and resource-bound tests.

Required interface:
- Byte/text encoding and length-unit contract.
- Immutable bounded strings, builders, slicing and checked concatenation.
- Generic typed List and Map APIs matching the source-language operations actually used by the compiler.
- Capacity growth with overflow checks and failure atomicity.
- Defined map collision and iteration-order semantics.
- Stable reference/handle semantics; no use-after-move or stale references.

Dependencies: N2 memory/object model. Do not consume PR #304 byte-output APIs as though they were integrated; first stabilise the CCAM semantic/version boundary.

Acceptance: exact source-runtime operation vectors, randomized/mutation tests, allocation-failure tests, aliasing tests and per-operation complexity/resource limits.

### N4 — Expand checked source lowering and native backend

Likely files:
- `verification/ccam_lowering.cap`
- `verification/ccam_native_x64.cap`
- canonical CCAM specification and schema files.
- new focused `verification/` tests per type/operation family.

Required interface:
- A typed, versioned CCAM representation for each new source construct.
- Explicit layouts and semantics for strings, lists, maps, records, enums and optionals.
- Defined evaluation order, ownership transfer/borrowing, traps and resource accounting.
- Backend ABI for object references, aggregate values and runtime calls.
- Fail-closed rejection of unimplemented features.

Dependencies: N1 and N2/N3. Add only features required by compiler bootstrap, then broaden to the full language by separate PRs.

Acceptance: frontend-to-CCAM conformance; CCAM validator rejection suite; native evaluator/backend outcome comparison; object/ABI tests; implementation refinement evidence per feature slice.

### N5 — Self-host compiler frontend

Likely files:
- `compiler/ast.cap`
- `compiler/lexer.cap`
- `compiler/parser.cap`
- `compiler/checker.cap`
- `compiler/ranges.cap` (initially optional/off)
- `verification/ccam_lowering.cap` and associated native backend tests.

Required interface:
- All compiler data types map to the N2/N3 object model.
- Bounded recursive parsing and AST allocation.
- Deterministic diagnostics and source spans.
- Full type/safety checker semantics.
- A conservative first profile may disable range-based check elimination and keep runtime checks; the existing checker and diagnostics must remain unchanged.
- Module/import loading remains a separate capability layer (N7).

Dependencies: N2/N3/N4. Use existing source and tests as a differential reference, not as proof.

Acceptance: same accepted/rejected corpus and exact diagnostics; fuzz/deep nesting/resource tests; source-to-CCAM correspondence for compiler code; no legacy runtime linkage.

### N6 — Native compiler backend (replace C codegen)

Likely files:
- Replace `compiler/codegen.cap` with a typed CCAM/object lowering interface or introduce `compiler/native_codegen.cap` and retire C codegen only after equivalence.
- `verification/ccam_native_x64.cap` or a production backend module once the interface is stable.
- `docs/architecture/CCAM.md` and target ABI documentation.
- compiler conformance and native executable tests.

Required interface:
- Checked frontend output -> canonical CCAM -> whole-program validation -> object/ELF.
- No generated C, no C compiler driver, no C linker, no C runtime.
- Deterministic diagnostics and object metadata.
- Explicit target triple/ABI, assembler/linker versions, relocation model, data sections and entry point.

Dependencies: N0-N5. Existing `compiler/codegen.cap` must not remain a hidden fallback.

Acceptance: compiler builds representative programs and the compiler itself; binary dependency closure audit; native-vs-reference semantic corpus; compiler/backend correctness evidence.

### N7 — Native CLI, imports, formatter and LSP

Likely files:
- `compiler/main.cap`
- `tools/fmt.cap`
- `tools/lsp.cap`
- new `runtime/native/io_linux_x64.cap`, `runtime/native/json.cap` or equivalent.
- capability and protocol documentation plus tests.

Required interface:
- Explicit read/write/argv/stdin/stdout/process-exit capabilities.
- Path confinement and bounded import graph/bytes.
- Atomic output publication.
- Bounded streaming JSON/JSON-RPC decoder/encoder, document map and cancellation.
- Formatter token-preservation and idempotence guarantees.

Dependencies: N2/N3 and native OS boundary; N1 is specifically CCAM interchange and must not be confused with LSP JSON.

Acceptance: no Python/C dependencies, filesystem capability tests, protocol fuzzing, framing limits, formatter idempotence and deterministic diagnostics.

### N8 — Independent S0 seed and S1/S2/S3 build policy

Likely files:
- `bootstrap/native-seed/` (new, separately audited implementation).
- `bootstrap/native/` (S1/S2 build scripts and manifests).
- `Makefile`, `bin/capstan`, `.github/workflows/*`, release/provenance scripts — only after native compiler and runtime are proven.
- `docs/architecture/NATIVE-BOOTSTRAP-PLAN.md` for versioned policy and evidence.

Required interface:
- S0 consumes a bounded source manifest and emits S1 executable or canonical native IR.
- S1 consumes compiler source and emits native executable.
- S2 is built by S1 from the same source/manifest.
- S3 release build runs with S0, Python and C toolchain unavailable.
- Build provenance binds all source, compiler, linker, assembler, environment and artifact hashes.

Dependencies: N4-N7. S0 must remain bootstrap-only; no ordinary production invocation.

Acceptance: clean independent seed builds, diverse seed comparison, reproducible output, dependency closure audit and semantic assurance separate from reproducibility.

## 3. Integration gates and branch discipline

1. **Do not rebase this research branch while the integration worker is actively changing mainline interfaces.** Refresh the baseline only after issue #370 coordination.
2. Before any shared-file implementation PR, record the target main SHA, relevant interface signatures and dependency PR merge status in issue #370.
3. Keep each PR narrow: semantic contract, implementation, conformance vectors and assurance evidence should be reviewable together but not mixed with unrelated compiler cleanup.
4. Do not cherry-pick unmerged PRs #315/#304/#246/#262/#255/#371/#372. Consume their merged mainline interfaces only after exact-head CI and review.
5. No PR may change the production compiler default or remove the C path until a native replacement passes the release gates.
6. If an integration conflict arises, stop and coordinate; do not rewrite another worker's history or resolve it by copying/forking their implementation.

## 4. Proposed release gates

| Gate | Required evidence |
|---|---|
| G0 — scalar native | Baseline native CI retained; full-width result/trap protocol; stronger ELF checks; resource adversarial tests |
| G1 — CCAM boundary | Stable strict decoder; whole-program validator; malformed-input and exact-number corpus |
| G2 — memory/runtime core | Concrete object model, bounded allocator, ownership/lifetime and failure atomicity evidence |
| G3 — compiler frontend | AST/lexer/parser/checker run on native runtime; diagnostic and source corpus agreement |
| G4 — native backend | Native compiler output for supported subset; no generated C or C runtime; backend correspondence evidence |
| G5 — self-host | S1 compiles compiler source; S2 rebuilt by S1; behavioral equivalence and identities |
| G6 — production | S3 reproducible independent builds, diverse bootstrap, no Python/C dependency closure, correctness and trust audit |

## 5. Current proposal status

This document is a sequencing/interface proposal only. It creates no new issue assignment, no PR and no shared implementation change. Exact line-level interfaces must be refreshed against the mainline after the integration worker stabilises the CCAM and runtime changes. The next implementation-ready unit is N0 (native terminal result contract) only after the relevant CCAM semantics are agreed.
